# Анализ чувствительности collaborative filtering

## Назначение

`evaluate_cf_sensitivity` проверяет, насколько метрики зависят от трёх настроек:

- `rating_threshold` — минимальная оценка, считающаяся положительным событием;
- `min_cooccurrence` — минимальное число совместных пользователей для связи пары материалов;
- `shrinkage` — сглаживание сходства редких пар.

Для каждой комбинации сравниваются `item_item_cf` и `content_cf_hybrid`. В результат входят Precision@K, Recall@K, NDCG@K и catalog coverage. Результаты агрегированы; идентификаторы пользователей не возвращаются.

## Запуск

Передать уже нормализованные `UserInteraction` и открытый каталог `CatalogItem`:

```python
from recommender.evaluation.sensitivity import evaluate_cf_sensitivity

rows = evaluate_cf_sensitivity(
    events,
    catalog,
    rating_thresholds=(3, 4, 5),
    min_cooccurrences=(1, 2, 3, 5),
    shrinkages=(0.0, 2.0, 5.0, 10.0),
    k=10,
)
for row in rows[:10]:
    print(row)
```

## Методология и ограничения

- Для каждого порога строится temporal validation holdout: последние события пользователя используются как validation, а профиль и CF обучаются только на событиях до соответствующей границы.
- Это этап выбора гиперпараметров. Нельзя выбирать конфигурацию по финальному test-набору и затем выдавать его метрики за независимую оценку.
- В текущей реализации веса content/CF в гибриде остаются фиксированными 0.5/0.5; этот эксперимент их не оптимизирует.
- Порог рейтинга меняет не только обучение CF, но и состав положительной validation-релевантности, поэтому сравнивать метрики разных порогов нужно с осторожностью.
- Нулевые и малые значения co-occurrence могут увеличить coverage, но не обязательно улучшают ранжирование.
- Если данных для конкретного порога недостаточно, конфигурации с пустым temporal split не возвращаются.
- Результаты нужно получить на разрешённой выгрузке; синтетические unit-тесты проверяют только механику вычислений, а не качество рекомендаций.
