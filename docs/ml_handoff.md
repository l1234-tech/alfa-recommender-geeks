# ML handoff: контракт рекомендательного модуля

Документ предназначен для команды backend/frontend. Он описывает фактически реализованные Python-контракты ML и предлагает нейтральную структуру передачи данных между компонентами. Это **не реализация API**, не FastAPI-код и не инструкция по Docker/deployment.

## 1. Границы ответственности

ML-часть находится в `recommender/` и отвечает за:
- нормализацию открытых метаданных каталога;
- построение профиля из onboarding и разрешённых взаимодействий;
- ранжирование кандидатов;
- фильтрацию недоступных, просмотренных и завершённых материалов;
- объяснение рекомендации и следующий шаг;
- offline evaluation.

Backend-команда отвечает за транспорт, HTTP endpoints, аутентификацию, хранение, валидацию внешних запросов и вызов ML. Frontend-команда отвечает за формы onboarding и отображение рекомендаций. Эти компоненты здесь не реализуются.

## 2. Python-контракты, реализованные сейчас

### CatalogItem

Источник: `recommender/models.py`.

| Поле | Тип | Обязательность | Значение |
|---|---|---|---|
| `item_id` | `str` | обязательно | ID материала в источнике |
| `item_type` | `str` | обязательно | Тип сущности: article/course/document/webinar/podcast/lesson/calculator |
| `title` | `str` | обязательно | Открытое название |
| `description` | `str` | нет | Разрешённое открытое описание |
| `topics` | `frozenset[str]` | нет | Темы |
| `tags` | `frozenset[str]` | нет | Теги |
| `industries` | `frozenset[str]` | нет | Отрасли |
| `is_available` | `bool` | нет, default true | Можно ли рекомендовать материал |
| `url` | `str | None` | нет | Ссылка на материал, если разрешено |

Ключ материала — пара `(item_type.casefold(), item_id)`. Один и тот же ID в разных типах сущностей считается разными объектами. Каталог не должен содержать повторяющиеся typed keys.

### UserProfile

Источник: `recommender/models.py`.

| Поле | Тип | Назначение |
|---|---|---|
| `topics` | `frozenset[str]` | Интересующие темы |
| `tags` | `frozenset[str]` | Интересующие теги |
| `industries` | `frozenset[str]` | Отрасли пользователя |
| `current_goal` | `str` | Текущая задача в свободном тексте |
| `preferred_types` | `frozenset[str]` | Предпочитаемые типы материалов |
| `completed_item_keys` | `frozenset[ItemKey]` | Уже завершённые материалы |
| `seen_item_keys` | `frozenset[ItemKey]` | Уже встречавшиеся материалы |
| `positive_item_keys` | `frozenset[ItemKey]` | Явные положительные сигналы |
| `positive_item_weights` | `tuple[(ItemKey, float), ...]` | Сила положительного сигнала; для отсутствующего веса используется 1.0 |

В текущем контракте **нет отдельных полей** `business_stage` и `experience_level`. Не передавайте их как будто модель уже их учитывает: пока эти признаки можно согласованно преобразовать в onboarding topics/tags на стороне подготовки профиля. Расширение модели требует отдельного ML-изменения и проверки влияния на алгоритмы.

### Recommendation

Источник: `recommender/models.py`.

| Поле | Тип | Значение |
|---|---|---|
| `item` | `CatalogItem` | Рекомендуемый материал |
| `score` | `float` | Внутренний ranking score |
| `reason` | `str` | Объяснение совпадения с профилем |
| `next_step` | `str` | Предлагаемое следующее действие |

`score` — не вероятность, не процент уверенности и не оценка качества материала. Не показывайте его конечному пользователю как «вероятность релевантности» без отдельной калибровки.

## 3. Рекомендуемый нейтральный формат передачи

Ниже — **предлагаемое отображение** Python-контрактов в JSON для согласования между командами. Это пример спецификации, не готовый endpoint и не существующий сериализатор.

Входной профиль для cold start:

```json
{
  "topics": ["маркетинг", "продажи"],
  "tags": ["начинающий"],
  "industries": ["retail"],
  "current_goal": "привлекать покупателей в магазин",
  "preferred_types": ["article", "course"]
}
```

Для профиля с историей дополнительно передаются типизированные ключи:

```json
{
  "seen_item_keys": [["article", "article-id-1"]],
  "completed_item_keys": [["course", "course-id-2"]],
  "positive_item_keys": [["lesson", "lesson-id-3"]],
  "positive_item_weights": [
    {"item_key": ["lesson", "lesson-id-3"], "weight": 1.0}
  ]
}
```

Предлагаемая форма одной рекомендации:

```json
{
  "item": {
    "item_id": "article-id-1",
    "item_type": "article",
    "title": "Маркетинг розничного магазина",
    "description": "Открытое описание материала",
    "topics": ["маркетинг"],
    "tags": ["рост"],
    "industries": ["retail"],
    "is_available": true,
    "url": "https://example.invalid/material"
  },
  "score": 0.42,
  "reason": "совпадают выбранные темы; материал связан с вашей отраслью",
  "next_step": "Открыть описание и проверить, подходит ли материал для вашей задачи."
}
```

Значения в примерах иллюстративные, не относятся к реальным материалам платформы. `example.invalid` — placeholder, не рабочая ссылка.

## 4. Вызов ML из Python

Реализованная функция ранжирования:

```python
from recommender.models import UserProfile
from recommender.ranking import recommend

profile = UserProfile(
    topics=frozenset({"маркетинг", "продажи"}),
    tags=frozenset({"начинающий"}),
    industries=frozenset({"retail"}),
    current_goal="привлекать покупателей в магазин",
)

recommendations = recommend(
    profile,
    catalog,
    limit=10,
    strategy="hybrid",
)
```

Доступные стратегии:
- `baseline` — метаданные и совпадение текста задачи;
- `hybrid` — TF-IDF + metadata baseline;
- `collaborative` — item-item CF, требует заранее построенный `collaborative_index`;
- `content_cf_hybrid` — контент + CF, требует `collaborative_index`.

Для collaborative-стратегий индекс строится из разрешённых событий и каталога через `ItemItemIndex.fit(...)`. Вызов `recommend(..., strategy="collaborative")` без индекса завершится `ValueError`. При отсутствии CF-сигнала content+CF hybrid использует контентную оценку.

## 5. Фильтрация и поведение

- Недоступные материалы исключаются.
- Уже просмотренные/встречавшиеся и завершённые материалы исключаются по typed key.
- Повторяющиеся ID разных типов не смешиваются.
- Если история отсутствует, baseline и content hybrid могут ранжировать по onboarding-профилю.
- Если профиль пуст, metadata baseline вернёт равные нулевые scores и детерминированный порядок по typed key; это не персонализированная рекомендация. Продуктовой команде следует решить, показывать ли общий каталог или запрашивать onboarding.
- Если кандидатов меньше `limit`, возвращается меньше результатов.
- `reason` и `next_step` возвращаются в каждой рекомендации; при отсутствии конкретного совпадения используется нейтральное объяснение.

## 6. Данные и приватность

- Использовать только открытые метаданные каталога, разрешённые для рекомендации.
- Не передавать закрытое содержимое платных материалов в признаки или объяснения.
- Не использовать IP как признак.
- Сырые пользовательские идентификаторы нужны только внутри обучающего/оценочного пайплайна; они не входят в `UserProfile` и не должны попадать в API-ответ.
- Анонимные рейтинги нельзя привязать к профилю пользователя.
- Отсутствие события не является отрицательной меткой.
- `CourseUserBindings` — записи о доступе/прогрессе, а не просмотры; положительным событием считается только подтверждённое завершение по принятому правилу.
- Семантика `RecommendedItems` не подтверждена, поэтому нельзя считать её положительной обратной связью без отдельной проверки.
- Не сохранять в логах полные профили и историю взаимодействий без обоснованной необходимости.

## 7. Ограничения качества

- Гибридные веса — экспериментальные настройки, не обученные вероятностные параметры.
- TF-IDF — лексическое сходство без лемматизации/стемминга.
- Нет исторических снимков каталога; при временной оценке возможно использование текущих метаданных.
- Cold-start benchmark синтетический и требует экспертной проверки.
- Офлайн-метрики и тесты не подтверждены запуском на реальной выгрузке в рамках этого PR.
- Рекомендации не должны трактоваться как доказательство качества или гарантированного бизнес-результата.

## 8. Что нужно согласовать командам

1. Согласовать JSON-представление typed keys и весов положительных сигналов.
2. Согласовать, какие onboarding-ответы отображаются в `topics`, `tags`, `industries` и `current_goal`.
3. Передавать ML только актуальный список доступных материалов с открытыми метаданными.
4. Согласовать стратегию и `limit`; collaborative-варианты требуют построения CF-индекса на разрешённой истории.
5. Согласовать, как UI показывает пустой профиль и пустую выдачу.
6. Не считать score вероятностью и не показывать закрытые поля каталога.
