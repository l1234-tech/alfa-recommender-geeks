# Анализ ошибок рекомендаций

Модуль `recommender.evaluation.error_analysis.analyze_recommendation_errors(events, catalog, k=10)` дополняет ranking-метрики диагностикой held-out положительных материалов. По каждому материалу назначается ровно одна категория:

- `recommended_in_top_k` — попал в первые K рекомендаций;
- `missing_from_catalog` — отсутствует в доступном каталоге для оценки;
- `unavailable` — присутствует, но помечен недоступным;
- `filtered_by_history` — исключён как уже встречавшийся или завершённый;
- `ranked_below_k` — кандидат допустим, но находится ниже K;
- `not_ranked` — кандидат не попал в полный ранжированный список.

Отчёт содержит только агрегированные количества и доли, без user_id и item_id. Поддерживаются baseline, hybrid, collaborative и content+CF hybrid. Для CF используется только допустимая предшествующая история из temporal split.

## Как читать результаты

- Большие `missing_from_catalog_rate` и `unavailable_rate` указывают на проблему покрытия/доступности данных, а не на качество ранжирования.
- Большой `ranked_below_k_rate` указывает на кандидатов, которые система нашла, но поставила слишком низко.
- `not_ranked_rate` требует проверки фильтров и согласованности каталога/ключей.
- `hit_rate@K` показывает долю релевантных held-out объектов, попавших в верхние K.

Категория `filtered_by_history` оставлена для диагностики, хотя текущий temporal holdout исключает из тестовой релевантности ключи, уже присутствовавшие в train. Поэтому в стандартном прогоне она обычно должна быть нулевой.

## Ограничения оценки

Это диагностика того же temporal validation/holdout, а не независимый test. TF-IDF использует текущий каталог; исторического снимка каталога нет, поэтому возможна утечка будущих метаданных. Отсутствие положительного события не трактуется как негативная метка. Результаты нужно интерпретировать только после запуска на разрешённой выгрузке; метрики на реальной БД здесь не заявляются.
