# План проверки эффекта и внедрения

Как убедиться, что персональные рекомендации повышают **конверсию в покупку**
образовательных продуктов и **частоту возвращения** на платформу.

## 1. Цели и метрики

**Главная (north-star):** средняя конверсия сессии в покупку платного материала.

**Вторичные (продуктовая цель кейса):**
- число активных дней пользователя за период (возвраты на платформу);
- CTR рекомендаций (клик по карточке / показ);
- доля покупок, пришедших из блока рекомендаций.

**Guardrail (не должны ухудшиться):** отписки/жалобы, доля сессий с мгновенным
уходом, нагрузка/латентность API.

**Воронка для анализа:** показ рекомендации → клик → просмотр материала → покупка.

## 2. Сначала офлайн, потом онлайн

**Офлайн (до выката).** На предоставленном датасете — временной holdout по
пользователю (train = прошлое, test = будущее), метрики `Precision@K`,
`Recall@K`, `NDCG@K` (реализованы в `recommender/evaluation`). Сравниваем наш
подбор с бейзлайном «по совпадению темы» и выбираем стратегию
(`baseline` vs `hybrid`) через `compare_content_models`. Это дёшево и отсекает
заведомо слабые варианты до трафика.

**Онлайн (после выката).** Офлайн-метрики не измеряют покупку напрямую, поэтому
решение о влиянии на конверсию принимаем по A/B-тесту.

## 3. Дизайн A/B-теста

| Параметр | Значение |
|---|---|
| Единица рандомизации | пользователь (стабильный хеш `user_id`, без PII) |
| Контроль (A) | текущий подбор по совпадению темы |
| Тест (B) | персональные рекомендации (наш сервис) |
| Сплит | 50/50, затем рамп 10%→50%→100% |
| Главная метрика | конверсия в покупку в течение 7 дней после сессии |
| Длительность | до набора мощности (см. ниже), минимум 1–2 недели для недельной сезонности |

**Мощность.** Базовая конверсия `p`, целевой подъём (MDE) например +10–15%
относительно. Нужный размер выборки на группу оцениваем стандартно
`n ≈ 16·p(1−p)/Δ²` (α=0.05, power=0.8) → из дневного трафика получаем
длительность. Фиксируем параметры ДО старта.

**Решение.** Выкатываем, если главная метрика статистически значимо выросла и
ни один guardrail не просел. Иначе — анализ сегментов и итерация.

## 4. Что нужно логировать (без персональных данных)

Событийный лог для расчёта метрик: `rec_request_id`, список показанных
`material_id` и их позиции, клики, просмотры, покупки, стратегия и признак
`cold_start`. Идентификаторы пользователя не логируются в открытые отчёты
(согласовано с ограничениями кейса и ML-пайплайном).

## 5. Внедрение (rollout)

1. Выкат за фиче-флагом, рамп 10%→50%→100% с контролем guardrail.
2. Мониторинг латентности `POST /api/v1/recommendations` и доли fallback-ответов
   (встроенный скорер вместо ML) — индикатор здоровья интеграции.
3. План отката: отключение флага возвращает подбор по теме мгновенно.
4. После стабилизации — A/B для выбора `baseline` vs `hybrid` уже на реальной
   конверсии, а не только на офлайн-метриках.

## 6. Риски измерения

- Отложенная покупка (длинный цикл решения) → основное окно атрибуции — 7 дней; дополнительное 14-дневное окно можно анализировать отдельно, если оно заранее зафиксировано и не подменяет главную метрику.
- Холодный старт: у новых пользователей мало истории → отдельно смотрим их
  сегмент (главная цель для них — рост активных дней, а не немедленная покупка).
- Новизна (novelty effect) → не фиксируем вывод по первым дням.
