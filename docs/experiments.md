# Эксперименты и оценка

## Оценка релиза на одном каталоге

Один каталог из PostgreSQL (1 153 доступных материала), 15 синтетических
профилей, включая три с историей, первые пять рекомендаций. Подбор по теме
использует совпадение темы и популярность. Обе стратегии API проверены
через HTTP на тех же материалах и профилях.

| Алгоритм | Precision@5 | nDCG@5 | nDCG@5 с историей |
|---|---:|---:|---:|
| Подбор по теме | 0,77 | 0,66 | 0,48 |
| API, контентное совпадение | 0,49 | 0,38 | 0,51 |
| API, гибрид с TF-IDF | 0,56 | 0,45 | 0,55 |

Гибрид — лучшая из двух стратегий API и выбран по умолчанию в Docker. **На
профилях с историей гибрид обходит подбор по теме: nDCG@5 0,55 против 0,48
(+15%)** — это ключевой для кейса сценарий, где учитывается история. Кроме того,
**100% рекомендаций API сопровождаются объяснением и следующим шагом, тогда как
подбор по теме не даёт их вовсе**, а кейс прямо требует объяснять каждую
рекомендацию.

Важно про методику: здесь бейзлайн усилен популярностью, тогда как кейс задаёт
сравнение с подбором по совпадению темы. Офлайн-оценка по записям на курсы
смещена в пользу популярного (его чаще выбирают независимо от конкретной задачи),
поэтому по Precision@5 на холодных профилях ожидаемо лидирует популярностный
бейзлайн. Истинная продуктовая ценность — подбор под задачу и рост покупок —
проверяется онлайн [A/B-тестом](ab_test_plan.md), а не офлайн-Precision@5.

Для повтора из корня проекта установите `backend/requirements.txt`,
запустите API с восстановленным каталогом и выполните:

```bash
DATABASE_URL=postgresql://alfa:alfa@127.0.0.1:5433/alfa_course \
  RECO_API_URL=http://127.0.0.1:8000 python -m tools.evaluate_delivery
```

Контроль использует агрегаты записей на курсы и рекомендаций других материалов.
Скрипт печатает только сводные метрики.

## Предыдущая оценка на отдельной выгрузке

Качество проверяем двумя способами:
1. **Тестовые профили.** Ручная разметка, проверяет сценарии из ТЗ: холодный старт, неполные данные, объяснения.
2. **Leave-one-out на реальных записях на курсы.** Проверяет, умеет ли алгоритм угадывать, что человек выберет на самом деле.

Данные: база `courses_for_bu`, выгрузка делается через `analytics/export_catalog.py`.
В каталоге 1139 опубликованных материалов: 838 статей, 247 документов, 33 курса,
13 вебинаров, 8 подкастов. Записей пользователей на курсы 10 050 (7 342 пользователя).
Особенности данных, которые влияют на оценку, описаны в [data_notes.md](data_notes.md).

## 1. Тестовые профили

`analytics/profiles/test_profiles.json`, 15 профилей. Они покрывают три персоны из ТЗ
и все сценарии проверки из приложения 2:

| Сценарий | Профили | Что проверяем |
|---|---|---|
| `full_profile` | p01, p02, p03, p08, p10, p12, p15 | персонализация по стадии/опыту/формату/отрасли |
| `cold_start` | p04 (пустой), p05 (только задача «продвижение бизнеса») | полезная выдача без данных |
| `partial_profile` | p09 («где брать покупателей»), p13 (опечатки) | свободный текст без терминологии |
| `with_history` | p07, p11, p14 | учёт истории, нет повторов |
| `no_match` | p06 (ветклиника, такой отрасли в базе нет) | общая подборка вместо пустоты |

Для каждого профиля записано, что ему подходит: группы тем, уровень, стадия, форматы.
История задана правилом («3 статьи по маркетингу») и собирается из каталога.

**Группы тем.** У курсов и статей в базе разные наборы тем, поэтому для оценки они
сведены в 10 групп (`THEME_MAP` в `analytics/config.py`): launch, taxes_law, finance,
marketing, sales, marketplaces, team, operations, strategy, cases.

**Релевантность материала**
- **2**: подходит группа темы, уровень, формат и стадия;
- **1**: подходит группа темы и уровень;
- **0**: не подходит или уже просмотрен.

Если уровень или стадия у материала не размечены (а это большинство статей), это не штрафуется.

| Метрика | Что показывает |
|---|---|
| Precision@K, nDCG@K, HitRate@K, MRR | точность и порядок выдачи |
| reason_rate / next_step_rate | у какой доли рекомендаций есть объяснение и следующий шаг |
| reason_unique | различаются ли объяснения (1.0 — нет шаблонных) |
| theme_div / format_div | разнообразие тем и форматов |
| paid_share | доля платных и подписочных (контроль навязчивости) |
| coverage | какая доля каталога вообще попадает в рекомендации |
| checks_passed | доля пройденных проверок: полная выдача, известные id, есть объяснение и шаг, бесплатный первым, не продвинутый первым для новичка, короткий первым, нет повторов |

### Результаты на реальном каталоге (K=5)

| Алгоритм | Precision | nDCG | HitRate | MRR | reason_unique | theme_div | format_div | coverage | checks |
|---|---|---|---|---|---|---|---|---|---|
| random | 0.28 | 0.25 | 0.60 | 0.34 | 0.00 | 0.79 | 0.39 | 0.06 | 0.57 |
| popular | 0.29 | 0.24 | 0.67 | 0.42 | 0.20 | 0.60 | 0.20 | 0.00 | 1.00 |
| topic_baseline | 0.81 | 0.69 | 1.00 | 0.91 | 0.20 | 0.47 | 0.31 | 0.03 | 1.00 |

nDCG@K по сценариям:

| Алгоритм | cold_start | full_profile | no_match | partial_profile | with_history |
|---|---|---|---|---|---|
| random | 0.50 | 0.19 | 0.51 | 0.22 | 0.16 |
| popular | 0.50 | 0.15 | 0.00 | 0.39 | 0.28 |
| topic_baseline | 1.00 | 0.66 | 1.00 | 0.43 | 0.65 |

**Где бейзлайн по теме слабый (здесь основной алгоритм должен выигрывать):**
- **Свободный текст.** На «где брать покупателей» nDCG 0.15: нет ключевого слова, и бейзлайн выдаёт популярное.
- **Нет персонализации по формату и стадии.** Кофейне с вопросом «когда платить УСН»
  (p02) он даёт пять курсов про 115-ФЗ вместо короткой статьи или календаря (nDCG 0.33).
- **Не смотрит на уровень.** Опытному в финансах (p08) первыми идут вводные курсы.
- **Не использует историю для подбора,** только исключает просмотренное (p11 — 0.64).
- **Шаблонные объяснения** (`reason_unique` 0.20) и **покрытие 3% каталога.** Популярность
  курсов на порядки выше, чем у статей, поэтому статьи (74% каталога) почти не показываются.

## 2. Leave-one-out на реальном поведении

`python -m analytics.offline_eval`. Берём 1 562 пользователя, у которых 2+ курса. Один
курс прячем, остальные отдаём алгоритму как историю. Смотрим, попадёт ли спрятанный курс
в топ-5. Даты есть только у 26% записей, поэтому прячем случайный курс (seed 42), а не
последний. Популярность для бейзлайнов пересчитана без спрятанных курсов.

| Алгоритм | HitRate@5 | MRR@5 |
|---|---|---|
| random | 0.000 | 0.000 |
| popular | 0.589 | 0.288 |
| topic_baseline | 0.617 | 0.320 |
| cooccurrence («кто проходил ваши курсы, проходил ещё…») | **0.726** | **0.542** |

Вывод: уже простая совместная встречаемость курсов даёт +11 п.п. HitRate и почти
вдвое лучший MRR по сравнению с бейзлайном по теме. Значит, историю в основном
алгоритме нужно использовать для подбора, а не только для исключения просмотренного.
Ограничение: курсов всего 33, и половину записей дают 3 курса (два из них про 115-ФЗ),
поэтому популярность здесь — очень сильный бейзлайн.

## 3. Как проверить влияние на конверсию после внедрения (A/B-тест)

**Гипотеза.** Персональные рекомендации с объяснением и следующим шагом повышают
конверсию в покупку и число дней с заходом на платформу по сравнению с подборкой
по совпадению темы.

**Дизайн**
- Единица рандомизации: пользователь. Группа выбирается по `hash(user_id) % 100`, поэтому один человек всегда видит одну версию.
- Контроль (A): подборка по совпадению темы. Тест (B): наш алгоритм.
- Перед стартом проводим A/A-тест на 1 неделю, чтобы проверить сплит и логирование.
- Раскатка: 10% трафика (проверка, что ничего не сломалось) → 50/50.

**Метрики**

| Тип | Метрика |
|---|---|
| Основная | конверсия в покупку или оформление подписки за 28 дней после первого показа |
| Вторичная (продуктовая цель ТЗ) | среднее число дней с заходом за 28 дней |
| Вторичные | CTR рекомендаций, доля начатых и завершённых курсов (`CourseUserBindings.IsCompleted`), время до первого открытого материала |
| Защитные | доля пропустивших онбординг, отписки и жалобы, отток, доля платных в выдаче, время ответа API |

**Размер выборки** при α = 0.05 и мощности 80%. Базовую конверсию нужно взять у
бизнеса: в выгрузке оплаты почти не отражены (`IsPaid` у 22 записей из 10 050).

| Базовая конверсия | Минимальный эффект (отн.) | Пользователей в группе |
|---|---|---|
| 3% | +10% | ~53 000 |
| 3% | +15% | ~24 000 |
| 5% | +10% | ~31 000 |

Если трафика не хватает, основной метрикой берём более чувствительную (CTR, записи
на курс, дни с заходом), а покупку оставляем вторичной.

**Длительность.** Не меньше 2 полных недель плюс 28-дневное окно наблюдения.
Досрочно тест не останавливаем.

**Анализ**
- Конверсия: z-тест для долей. Дни с заходом: t-тест или бутстрэп. Для снижения дисперсии можно применить CUPED.
- Разрезы: новые (холодный старт) и с историей, заполнил онбординг или пропустил, персоны.
- Раскатываем, если основная метрика выросла значимо и защитные не ухудшились.

**Что логировать.** Показ (user_id, material_id, позиция, версия алгоритма, текст
объяснения), клик, открытие, запись на курс, завершение, покупка, ответы и пропуск
онбординга. В текущей базе нет событий по статьям и документам и почти нет дат,
поэтому без такого логирования эффект не измерить.
